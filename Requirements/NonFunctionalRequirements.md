## Overview

This page documents non-functional requirement the solution must follow.

* All secrets (authtokens or otherwise) must be stored using VS Code's secret storage
* Every file the solution writes to the local project structure — downloaded Entra artifacts and `connections.yaml` alike — must be serialised as YAML, not JSON, so that users can add explanatory comments to a hand-maintained file (for example, why a permission grant or role assignment exists, or why a connection is configured the way it is) without breaking it
* The project must be developed inside a VS Code Dev Container, defined in `.devcontainer/` and committed to source control, so that every contributor gets the same Node.js/TypeScript toolchain without installing it on the host
* Claude Code's knowledge and session data (its config, memory, and per-project session history) must be identical whether Claude Code is run on the host or inside the devcontainer for this project — not merely surviving a container rebuild, but requiring no export/import step when moving between the two. This also requires the devcontainer to mount the project workspace at the same absolute path inside the container as on the host, since Claude Code keys per-project session/memory storage off that path
* The devcontainer must give the container access to the host user's SSH keys (`~/.ssh`) so that authenticated git operations (clone/fetch/push over SSH) work from inside the container without provisioning separate keys
* The project must build and run on the latest Active LTS release of Node.js, using Microsoft's official Node/TypeScript devcontainer image (`mcr.microsoft.com/devcontainers/typescript-node`) pinned by Node major version and Debian variant in `.devcontainer/devcontainer.json` (e.g. `24-bookworm`) — not the untagged/`latest` image, which floats onto whatever major is newest. Only major-level tags receive Microsoft's ongoing OS security patches, so this is a deliberate major-version pin, not an exact patch pin. That major version must be bumped whenever a newer Node LTS is promoted, checked against https://nodejs.org/en/about/previous-releases rather than assumed
* The solution should carry near-100% unit test code coverage of its logic (connection storage, the add/edit connection form's validation, the auth service, tree providers, artifact serialisation, etc. as each is built), enforced via a coverage threshold in the test tooling rather than left as an unchecked aspiration — coverage of thin VS Code glue code (activation wiring, webview HTML templates) is a reasonable exception where a unit test would mostly be re-asserting the framework
