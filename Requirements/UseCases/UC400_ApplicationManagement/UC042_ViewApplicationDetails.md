# UC042 — View Application Details

## Overview

This use case details the structured editor a user sees when clicking an application node under **Applications** (see [UC041 — Browse Application Definitions](UC041_BrowseApplicationDefinitions.md)) — one editable view of all four of an application's files (see [UC040 — Define an Application](UC040_DefineApplication.md)), replacing the need to open each raw file separately to see or change it. All four files — `AppConfig.yaml` and the three `.yaml.j2` templates — are parsed into structured fields and re-serialized as YAML on save; none of them is treated as an opaque blob of text (see Postconditions for the comment/formatting tradeoff this implies).

This opens as a genuine VS Code **Custom Editor** tab (`ApplicationEditorProvider`, view type `entra.applicationEditor`) rather than a plain webview panel — the specific reason being that its tab then shows VS Code's normal unsaved-changes dot the moment any field is edited, and the tab participates in VS Code's native save (Ctrl+S, the Save command, or the in-form Save button — all equivalent), revert, close-with-unsaved-changes-prompt, and hot-exit/crash-recovery behavior, the same as any ordinary file. This is deliberately not something built by hand on top of a plain webview: VS Code has no concept of "unsaved" for a plain `WebviewPanel` at all, so getting the native indicator and lifecycle required this move to a Custom Editor. Because there's no single real file backing an application folder's four files at once, the tab's identity is a synthetic URI (`entra-application-editor:` scheme, encoding the folder's real URI — see [UC041](UC041_BrowseApplicationDefinitions.md)'s Related section for the sibling `entra-application:` scheme used by the plain-text combined-document alternative).

This is deliberately **not** the shared artifact-viewer webview used elsewhere (see [UC032](../UC300_ArtifactBrowsing/UC032_PreviewArtifactBeforeDownload.md)/[UC033](../UC300_ArtifactBrowsing/UC033_ViewLocalProjectArtifacts.md)) — that one is read-only by construction, because it shows a downloaded Graph snapshot. An application definition is hand-authored source with no such snapshot to defer to, so this view is directly editable, the same way [UC012](../UC100_Security/UC012_AddConnection.md)'s connection form is.

## Actors

* **User**
* **Extension**

## Preconditions

* An application definition exists as a folder under `<artifactsRoot>/Applications/` (its four files, per UC040, may be partially or fully present — this use case tolerates any of them being missing).

## Main Flow

1. User clicks an application node under **Applications** (see [UC041](UC041_BrowseApplicationDefinitions.md)).
2. The extension loads and parses all four of that application's files. A missing `AppConfig.yaml` is treated as blank metadata with no variables or environments, not an error; a missing `.yaml.j2` template is treated as an empty/default document for its section (no fields, `AzureADMyOrg` as the default sign-in audience where relevant) rather than an error.
3. The extension opens a Custom Editor tab (one per application folder — clicking an application whose view is already open brings that existing tab forward rather than opening a duplicate, the same as opening any file that's already open) with:
   * **Application name** and **Business unit** — the two plain metadata fields from `AppConfig.yaml`.
   * **Default variables** — a collapsible box (collapsed by default, its summary showing a live row count and the same ▶/▼ chevron as the other collapsible boxes in this form); inside it, a dynamic list of key/value rows, one per entry in `AppConfig.yaml`'s `Variables` map (the values shared as defaults across every environment), with controls to add or remove rows.
   * **Environments** — the whole section is a collapsible box (collapsed by default, its summary showing the environment count and a ▶/▼ disclosure chevron — as do all the collapsible boxes in this form); inside it, each environment is *itself* a collapsible box (same treatment as Exposed API scopes below — collapsed by default when the tab is opened, expanded when newly added via **+ Add environment**), its `<summary>` showing that environment's `name` and `environment_code` (updating live as either is edited). Expanded, each environment carries the four fixed fields — `Name` / `Publisher domain` / `Tenancy type` / `Environment code`, each with its own label — plus its own **Redirect URIs** (three lists — see below) and its own **Variables owned by this environment** list (see below). `tenancy_type` is a **Workforce**/**CIAM** dropdown (see [UC040](UC040_DefineApplication.md) for what the two values mean), not free text — a new row defaults to Workforce; a value already on disk that matches neither (there is no hard validation forcing it to, since this field is written by both this form and [UC035](../UC300_ArtifactBrowsing/UC035_DownloadApplicationArtifact.md)'s download path) is not specially preserved and is replaced with the dropdown's default the next time the row is rendered.
     * **Redirect URIs** — three dynamic lists inside each environment card, one per Entra redirect-URI category: **Web redirect URIs**, **Public client redirect URIs**, and **SPA redirect URIs**. Redirect URIs are defined per deployment target (they can legitimately differ between Dev, Test, Prod, etc.), so they live on the environment rather than on the App Registration section. Each list is stored as an *array-valued* entry in that environment's own `Variables` map — under the keys `web_redirectUris`, `publicClient_redirectURIs`, and `spa_redirectURIs` respectively (the mixed `Uris`/`URIs` casing is deliberate, matching what deploy tooling expects) — so `Application.yaml.j2` can reference them as `{{ environment.Variables.web_redirectUris }}` etc. at deploy time. An empty list writes no key. These three keys are edited only through these lists, never shown as rows in the generic **Variables owned by this environment** list below.
     * **Variables owned by this environment** — a dynamic key/value list inside each environment card, one row per entry in that environment's *own* `Variables` (the subset that isn't just an inherited shared default — see step 6 and [UC040](UC040_DefineApplication.md), and excluding the three redirect-URI keys above), edited exactly like the top-level **Default variables** section. This is where the per-environment GUID an **Exposed API scope**'s **ID variable name** generates (step 6) shows up and can be edited or given a real value. The shared defaults from the top-level **Default variables** section are *not* repeated here — they apply to every environment already and are edited once, up there.
   * **Dependencies** — the whole section is a collapsible box (collapsed by default, its summary showing a live row count and the same ▶/▼ chevron as the other collapsible boxes in this form); inside it, a dynamic list of rows, one per entry in `AppConfig.yaml`'s `Dependencies` map, each with a `Reference key` text field (the name used from a template, e.g. `SampleAPIApp`) and an `Application` dropdown populated from the other application folders that already exist under `<artifactsRoot>/Applications/` (the application being edited excluded from its own list) — the target application is **selected, not typed**, so a dependency can't be saved pointing at an application that doesn't exist in the project. If a previously-saved reference points at an application folder that's since been renamed or removed, its value is still shown as a selectable option (alongside the current real folders) so it isn't silently discarded by opening and re-saving this form.
   * **Application (App Registration)** — the whole section is a collapsible box (collapsed by default, same chevron/behaviour as the others; no count, since it's mostly fixed fields). The App Registration's `web` / `publicClient` / `spa` redirect blocks are not shown here — they're generated on save from the per-environment redirect-URI lists (see step 5's Redirect URIs and the Postconditions). Parsed from `Application.yaml.j2`: a **Display name** text field, a **Sign-in audience** dropdown (the four values Graph accepts: `AzureADMyOrg`, `AzureADMultipleOrgs`, `AzureADandPersonalMicrosoftAccount`, `PersonalMicrosoftAccount`), and a dynamic list of **Required permissions** (its own collapsible box *nested inside this one* — collapsed by default, summary showing a live row count) — one row per individual permission with `Resource app ID` / `Permission ID` / `Type` (`Scope` or `Role`) fields. `Resource app ID` is a dropdown of **Microsoft Graph** plus one option per reference key currently defined in the **Dependencies** section above — not free text — since a required permission's resource is expected to be either Microsoft Graph or another application definition in this same project: choosing Microsoft Graph stores the well-known Microsoft Graph application ID; choosing a Dependency stores a Jinja reference in the same form Dependencies itself uses, `{{ dependency_refs.<reference key>.applicationId }}` (e.g. `{{ dependency_refs.SampleAPIApp.applicationId }}`), resolved once deploy tooling exists from that dependency's own prior deploy result (see [UC040](UC040_DefineApplication.md)). The dropdown's Dependency options track the Dependencies section live as rows are added, renamed, or removed, so a dependency just added in the same editing session is immediately selectable. When a `Resource app ID` value already on disk is neither the Microsoft Graph ID nor a reference to a *currently defined* Dependencies key (a hand-edited file, a reference to a dependency since renamed or removed, or a raw third-party GUID this dropdown doesn't model) — checked once, when the tab is opened — that row shows the raw value as plain, still-editable text with a ⚠ warning icon next to it instead of the dropdown, rather than silently discarding or misrepresenting it; a newly added row always starts as a working dropdown.

     `Permission ID` is itself a dropdown too, populated from whichever resource is selected in that same row's `Resource app ID`: for **Microsoft Graph**, from the same checked-in permission catalogue [UC034](../UC300_ArtifactBrowsing/UC034_PreviewApplicationArtifact.md)'s read-only preview already resolves names from — choosing one stores its real, fixed Graph permission GUID, same as before this dropdown existed; for a **Dependency**, from that dependency's own **Exposed API scopes** (below) — the delegated scopes it defines for other applications to request — but choosing one stores that scope's **value** (its name, e.g. `access_as_user`), not its GUID: unlike Microsoft Graph's fixed permission IDs, a dependency's own scope GUID isn't necessarily fixed at authoring time (it may itself be an `{{ environment.Variables.<name> }}` reference — see the Exposed API scopes' **ID variable name** field below), so the actual GUID can only be resolved once deploy tooling exists, by matching this stored value against that dependency's *deployed* scopes for the same environment — the same deferral `{{ dependency_refs.<key>.applicationId }}` already relies on for `Resource app ID` itself. There is no local equivalent of an application-permission Role to offer for a dependency, since this schema doesn't model an application's own `appRoles`. Each option is labelled with its human-readable name/value and its type (e.g. "User.Read (Scope)"), and picking one automatically sets the row's `Type` dropdown to match — the two aren't independently editable once a known permission is picked, since a permission's type isn't a separate choice in Graph. Switching a row's `Resource app ID` immediately rebuilds its `Permission ID` options to match the new resource, resetting the row's `Permission ID` to blank in the process — the two resources' permission IDs are different namespaces entirely, so whatever was selected/typed for the previous resource is never valid for the new one and would otherwise show up as a spurious unmatched value (a dependency added in this same editing session isn't reflected in another row's options until the tab is reopened or reverted, since resolving a dependency's options reads that dependency's own file). When a resource has no options at all here (an unrecognised `Resource app ID`, or a Dependency that currently exposes no scopes), `Permission ID` falls back to plain free text, same as before this dropdown existed; a value already on disk that doesn't match any of a resource's *known* options is shown as text with the same ⚠ warning-icon convention `Resource app ID` itself uses, rather than a dropdown that can't represent it — except a blank `Permission ID`, which is simply an unfinished new row, not treated as a warning. Graph's nested `requiredResourceAccess[].resourceAccess[]` shape is flattened to this one row per permission for editing, and regrouped by `resourceAppId` back into that nested shape on save (see Postconditions). Also a dynamic list of **Exposed API scopes**, parsed from `Application.yaml.j2`'s `api.oauth2PermissionScopes` — the mirror image of Required permissions (what this application *exposes* rather than what it *requests*). The whole list is a collapsible box too (collapsed by default, summary showing a live scope count). Each scope inside it is *also* its own collapsible box, collapsed by default when the tab is opened (a scope newly added via **+ Add scope** starts expanded instead, since it needs filling in immediately) — collapsed, it shows just its **Scope value** and **ID variable name** (if set) as a one-line summary, updating live as those two fields are edited, so a specific scope stays identifiable without expanding it; clicking anywhere on that summary line expands or re-collapses the box. Expanded, every field has its own label: `Scope value` (e.g. `Files.Read`), `ID variable name`, `Type` (a `User`/`Admin` dropdown), `Enabled` (a checkbox), and `Admin consent display name`/`Admin consent description`/`User consent display name`/`User consent description` text fields. Each scope's Graph-required `id` (a GUID) is generated automatically the first time a scope is added or loaded without one, and is otherwise carried unchanged; giving a scope an **ID variable name** (e.g. `MyNewPermissionVariableName`) instead writes its `id` as a Jinja reference, `{{ environment.Variables.<name> }}` (e.g. `{{ environment.Variables.MyNewPermissionVariableName }}`), so the real value can be parked per environment (see step 5) rather than fixed once at authoring time — clearing that field back to blank on a later edit falls back to whatever raw id was already stored, rather than producing a broken reference to an empty name.
   * **Federated Credentials** — the whole section is a collapsible box (collapsed by default, summary showing a live credential count). Parsed from `FederatedCredentials.yaml.j2`: a dynamic list of credentials, each *itself* its own collapsible box (same treatment as Exposed API scopes above, and for the same reason — several free-text fields per entry would wrap unreadably as a single-line row): collapsed by default when the tab is opened, showing just its `Name` and `Subject` as a one-line summary that updates live as either is edited; a credential newly added via **+ Add federated credential** starts expanded instead. Expanded, every field has its own label: `Name` / `Issuer` / `Subject` / `Description` text fields and an `Audiences` field edited as a single comma-separated text value (Graph's `audiences` is a list, but is almost always single-valued in practice — the comma-separated field avoids a nested list-of-lists control while still round-tripping multiple values).
   * **Service Principal** — the whole section is a collapsible box (collapsed by default; no count). Parsed from `ServicePrincipal.yaml.j2`: an `App ID` text field, an `App role assignment required` checkbox, a read-only **Generated tags** preview (see below), and a dynamic list of custom **Tags**. On save the file also gets a `replyUrls` key written automatically (see step 7 and Postconditions) — it is not shown or editable in this form.
   * The **Generated tags** preview shows four tags computed live from the **Application name** and **Business unit** fields above, following a fixed convention:
     * `AppName:<Environment>_<Business unit>_<Application name>`
     * `Environment:{{Environment}}`
     * `<Application name>`
     * `BusinessUnit:<Business unit>`

     `<Environment>`/`{{Environment}}` are left literal in both forms shown — there is no single environment value to substitute at this point, since one application definition renders once per `Environments` entry (see UC040). This preview is read-only and **not saved by this form** — it does not get written to `ServicePrincipal.yaml.j2`'s `tags` list, and is shown purely so an author can see the convention their organization's future deploy tooling is expected to apply automatically at deploy time. It updates as the Application name/Business unit fields are edited, before Save is selected. Because these tags are applied automatically at deploy time, a custom Tag starting with `AppName:`, `Environment:`, or `BusinessUnit:` is rejected on save (see A2) — a custom tag can never collide with, or be mistaken for, one of these generated ones.
   * Every text field accepts Nunjucks placeholders (e.g. `{{ name }}`, `{{ environment_code }}`) as literal text — the form does not evaluate or resolve them, it only reads and writes whatever string is present.
4. As soon as the user changes any field, the tab shows VS Code's normal unsaved-changes dot — this happens on every edit (keystroke, add-row, remove-row), not only when Save is explicitly selected, the same as typing in any other document.
5. User selects **Save** (the in-form button, Ctrl+S, or VS Code's Save command — all trigger the same native save flow). At that point the extension validates: Application name is non-empty; no two Variable rows share a key and no row has a value without a key — for both the top-level **Default variables** and each environment's own **Variables owned by this environment** list (an environment-scoped failure names the environment); no two Environment rows share a name (case-insensitively); every Dependency row has both a reference key and a selected application with no two rows sharing a reference key; and no custom Tag starts with a reserved prefix (`AppName:`, `Environment:`, `BusinessUnit:` — see below) — a row that is entirely blank in any of the dynamic lists (Variables, Environments, Dependencies, the per-environment Redirect URIs, Required permissions, Federated Credentials, Tags) is treated as an unused spacer and silently dropped, not an error (an environment card that's blank apart from a variable or a redirect URI the user typed is *not* a spacer — it blocks save with a missing-name error rather than silently discarding that entry). Beyond that, the Application/Federated Credentials/Service Principal fields have no hard validation — any string a user types (including a malformed GUID or an empty required field) is accepted and saved as-is, since these files describe a future Graph payload the extension does not itself submit. If validation fails, VS Code reports the save as failed (its usual error notification) and an inline error is also shown next to the relevant section in the form — any collapsed section holding the error is automatically expanded (including its parent, for the sections nested inside Application) and scrolled into view so the message isn't hidden; the tab stays open, dirty, and unsaved — nothing already entered is discarded (see A2).
6. Before writing, the extension rebuilds each Environment entry's full effective `Variables` map: it folds that environment's three **Redirect URIs** lists into its own `Variables` as array values (`web_redirectUris` / `publicClient_redirectURIs` / `spa_redirectURIs`, each omitted when empty); then, every key from the top-level **Default variables** section above is merged into that environment's own entries (the environment's own value for a key wins if it has one); then, for every **Exposed API scope** with an **ID variable name** set, that name is added as a key to every environment that doesn't already have it, with a freshly generated GUID as its value — so `{{ environment.Variables.<name> }}` resolves to something in every environment once deploy tooling exists, without ever overwriting a value an environment already has. When writing `AppConfig.yaml`, that full per-environment set is written back out using the `Variables: &DefaultVariables` / `<<: *DefaultVariables` YAML anchor/merge-key convention [UC040](UC040_DefineApplication.md) describes — an environment's own file only lists keys that actually differ from (or don't exist in) the shared defaults, which is exactly what its **Variables owned by this environment** list shows; the rest come from the alias, the same as if a developer had written it that way by hand.
7. The extension re-serializes all four files as YAML from the structured fields and writes them to the application's folder. The tab's unsaved-changes dot clears (VS Code's native behavior for any successful save) and a confirmation is shown; the tab itself stays open, showing what was just saved.

## Alternate Flows

### A1 — User discards unsaved changes

1. The user selects **Discard unsaved changes** in the form (or triggers VS Code's own Revert File command on the tab) while it has unsaved edits.
2. The extension asks VS Code to revert the document; the tab reloads the four files fresh from disk, discarding whatever was entered, and its unsaved-changes dot clears. The tab itself stays open, now showing the last-saved state.

### A1a — User closes the tab with unsaved changes

1. The user closes the tab (or VS Code as a whole) while it has unsaved edits.
2. VS Code shows its normal "Do you want to save the changes you made to *(application name)*?" prompt — Save, Don't Save, or Cancel — the same as closing any other unsaved file. This is new behavior versus the plain-webview form this use case replaces, which had no such protection and silently discarded unsaved edits on close.
3. **Save** runs the same validation and write as the Main Flow's step 5; **Don't Save** discards the edits and closes the tab; **Cancel** leaves the tab open, unsaved.
4. If VS Code or the extension host is closed/crashes while the tab has unsaved edits, VS Code's hot-exit/backup mechanism (`backupCustomDocument`) restores those edits the next time the tab is reopened, the same as it does for any other unsaved file.

### A2 — Validation failures

1. **Missing Application name** — blocks save with an inline error on that field.
2. **A Variable row has a value but no key** — blocks save; the extension does not guess a key or silently discard a value the user typed. Applies to both the top-level **Default variables** and any environment's own **Variables owned by this environment** list (the latter names the environment).
3. **Two Variable rows share the same key** — blocks save, naming the offending key (and, for an environment's own Variables, the environment).
4. **An Environment row has other fields (a variable, or a redirect URI) filled in but no name** — blocks save, since `name` is how an environment is identified.
5. **Two Environment rows share the same name** (case-insensitively) — blocks save, naming the offending environment.
6. **A Dependency row has an application selected but no reference key** — blocks save; the extension does not invent a key.
7. **A Dependency row has a reference key but no application selected** — blocks save, naming the offending key.
8. **Two Dependency rows share the same reference key** — blocks save, naming the offending key.
9. **A custom Tag starts with a reserved prefix** (`AppName:`, `Environment:`, or `BusinessUnit:`) — blocks save, naming the offending tag and prefix; these prefixes are reserved for the Generated tags preview (step 3) applied automatically at deploy time, and a custom tag starting with one would collide with or be mistaken for a generated one.

## Postconditions

* `AppConfig.yaml` and all three `.yaml.j2` templates on disk reflect exactly what was in the form when **Save** was selected.
* **Known limitation, accepted deliberately for this version:** every one of the four files is parsed to structured fields and re-serialized fresh on save (none is edited in place or treated as opaque text), so saving drops:
  * any hand-written YAML comments in any of the four files;
  * any *other* YAML anchor/alias use beyond `AppConfig.yaml`'s own `Variables: &DefaultVariables` / per-environment `<<: *DefaultVariables` merge key, which this form specifically reconstructs on every save (see step 6) rather than losing — see `buildAppConfigNode()`'s doc comment in `types.ts` for how;
  * any keys beyond the ones this form models — e.g. an `Application`/`FederatedCredentials`/`ServicePrincipal` key this use case's field list (step 3) doesn't cover, such as `identifierUris`, `appRoles`, or `implicitGrantSettings` on `Application.yaml.j2`.

  This is an explicit, accepted tradeoff, not an oversight: a developer who needs to preserve a comment or unmodelled field across an edit made through this form manages that the same way they'd manage any other unreviewed change — by reviewing the `git diff` this use case produces before committing it, and re-adding anything the form dropped if needed.
* An Environment entry's own `Variables` map (distinct from the top-level **Default variables** section, see step 6) is editable as the **Variables owned by this environment** key/value list inside that environment's card, plus the three **Redirect URIs** lists which are stored as array-valued entries in the same map (`web_redirectUris` / `publicClient_redirectURIs` / `spa_redirectURIs`). Only the environment's *own* keys — the ones that differ from, or don't exist in, the shared defaults (redirect-URI keys always qualify, since the shared defaults are only ever plain strings) — appear there; the shared defaults themselves are edited once in the top-level **Default variables** section and merged in at save time (step 6). Removing an inherited shared default *from a single environment* isn't expressible through this form (the merge/alias always brings it back); use the "Open as Document" combined text view ([UC041](UC041_BrowseApplicationDefinitions.md)) for that.
* Redirect URIs are **not** written to `Application.yaml.j2` as a literal `web`/`publicClient`/`spa` block — that file carries no redirect URIs of its own. They live only in each environment's `Variables` (above), for deploy tooling to apply per target.
* No network call, authentication, or Graph interaction happens as a result of this use case — saving an application definition is entirely local, the same as UC040/UC041.
* The tab's title is the plain application name (e.g. "sample-web-app"), not the URL-encoded folder path the tab's underlying virtual URI actually contains — VS Code derives a Custom Editor's tab title from its document URI's path, and `webviewPanel.title` can't override that (see `applicationEditorUri.ts`), so the encoded folder location is carried in the URI's query string instead, keeping the path itself just the application name.
* The Service Principal section's **Generated tags** preview is never written to `ServicePrincipal.yaml.j2` — saving does not add, remove, or otherwise change anything in the `tags` list beyond what the custom Tags rows specify. Applying the generated tags to a deployed Service Principal is future deploy tooling's responsibility (see [Architecture/future_considerations.md](../../../Architecture/future_considerations.md)), not this use case's.
* Two of the four files get **generated redirect-URI blocks** on every save, written as Jinja2/Nunjucks `{% for %}` loops (see [UC040](UC040_DefineApplication.md)) that render to real arrays pulled from the per-environment redirect-URI variable lists (step 5's Redirect URIs), each `| default([])` so a category the environment doesn't define contributes nothing:
  * `Application.yaml.j2` — `web.redirectUris`, `web.redirectUriSettings` (an array of `{ "uri": …, "index": null }` objects — `index` always `null`), `publicClient.redirectUris`, `spa.redirectUris`.
  * `ServicePrincipal.yaml.j2` — `replyUrls` (the three lists concatenated into one array).

  Because those loop lines aren't valid YAML on their own, the editor strips any `redirectUris:` / `redirectUriSettings:` / `replyUrls:` line from the file (and from the combined "Open as Document" text) before it parses, and re-emits the loops on save. They are not editable fields and are not read back — whatever was there is replaced on save, the same as the App ID / audience / permissions round-trip. The redirect URIs themselves are still authored per environment (step 5).
